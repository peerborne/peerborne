Build the repository with the [source quick start](../quick-start/) first. The
eleven `@peerborne/*` packages are unpublished workspaces. Use these files in a
browser React/TypeScript project with `@peerborne/core`,
`@peerborne/automerge`, `@peerborne/react`, React, and React DOM installed, as
the next section shows. Automerge's browser build also needs Vite's WASM
setup; the
[wiki example configuration](https://github.com/Peerborne/peerborne/blob/main/examples/wiki-swarm/vite.config.ts)
shows the required plugins. This is a local document exercise, with no relay or
second identity required.

## Use the packages in another project

Create the application outside the Peerborne checkout. Adding it as a
workspace of the checkout changes the root `yarn.lock`, so
`yarn install --immutable` then fails. Instead, pack the libraries as
tarballs in the checkout and install them in the application:

```sh
# In the Peerborne checkout, after yarn install --immutable and yarn build.
# The directory must be outside the checkout; release:prepare replaces it.
yarn release:prepare ~/peerborne-packages

# In the application directory:
npm install ~/peerborne-packages/*.tgz react-dom
npm install --save-dev vite @vitejs/plugin-react vite-plugin-wasm typescript
```

`release:prepare` packs all eleven libraries and writes
`release-manifest.json` beside the tarballs. Installing every tarball at once
lets npm resolve the packages' dependencies on each other, such as
`@peerborne/react` on `@peerborne/store`, from those files rather than the
registry. npm also installs their peer dependencies, including React and
Automerge; React DOM is added explicitly. Repeat both steps after pulling new
Peerborne sources. Release validation installs the tarballs the same way in a
clean npm project.

This exercise creates a fresh, non-extractable signing key on every page load.
A reload therefore creates a **new identity**. Before building a persistent
application, design storage for the signing identity, the KEM key pair, and an
[encrypted checkpoint](../../concepts/storage/#local-checkpoints) of each
document, which holds its keys and state; see
[Identities](../../concepts/identities/). A document path
alone does not give another client its keys or access.

`change` returns `void` and does not catch the change's promise, so a
rejection becomes an unhandled promise rejection. This compact component
demonstrates the subscription API; use `await document.change(...)` with
application error handling when a save action must report authorization,
storage, or signing failures. A committed change that does not reach a member
resolves and is reported as `deliveryFailure` instead. See the
[React integration guide](../../cookbook/react/) for lifecycle details.

## Connect another client

Pass your relay's dialable multiaddr to `defaultBootstrapConfig` instead of an
empty list; see [Run your own relay](../../cookbook/running-a-relay/). An empty
bootstrap list creates a local node with no configured bootstrap peers.
Connecting does not onboard a new identity. Use the current
[signed invitation flow](../../cookbook/invitations/) to share with one online
collaborator, and review its membership and recovery limits.

Opening the same path on another node is not onboarding either. The hook's
default `'open'` mode loads from peers and requires
`resolveLoadSecurityCommitments` and `resolveTrustedDocumentWriters` in the
node configuration. If no connected peer can serve the path (a relay cannot),
it reports `No document state is available…`; if one can and
`resolveLoadSecurityCommitments` is missing, it reports a
`TrustedLoadSecurityCommitmentsError`. See
[Open existing documents](../../concepts/documents/#open-existing-documents).

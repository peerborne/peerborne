## What is Peerborne?

Peerborne is a set of **composable TypeScript libraries** that let you build applications where documents live on user devices and sync directly between peers — encrypted, signed, and content-addressed. There is no application database server. Relays carry ciphertext without seeing plaintext.

A centralized database is simpler and should be the default for most applications. Peerborne is for cases where central custody of plaintext—or dependence on one always-reachable application server—is the downside you need to remove.

## Try the initial-release demo

[Peerborne Note](https://try.peerborne.io/) is a small, real
Peerborne-and-Automerge application. Create a note locally, choose read-only or
editing access, and send one invitation link to a collaborator. Document data
is encrypted before it crosses the relay; the relay can still observe
connection and traffic metadata and can drop or delay traffic.

Both browsers must remain open and online while the first recipient claims the
15-minute invitation. Peerborne Note is early-stage and not production-ready:
do not use it for sensitive or durable data, and do not rely on identity or
document recovery, automatic reconnect, revocation UX, or relay failover.

## A Yjs document in a few lines

Once a Peerborne node is configured with the Yjs adapter, documents feel like
familiar CRDT shared types wrapped in encryption and access control:

```ts
import { Peerborne, SubtleCrypto, defaultConfig,
  defaultBootstrapConfig } from '@peerborne/core';
import { YjsProvider, YjsACLProvider,
  YjsKeychainProvider, YjsJSONSerializer } from '@peerborne/yjs';

// The application must supply an ECDSA P-384 key pair:
const userKeyPair = await crypto.subtle.generateKey(
  { name: 'ECDSA', namedCurve: 'P-384' },
  true,
  ['sign', 'verify'],
) as CryptoKeyPair;

const swarm = new Peerborne(
  userKeyPair.privateKey,
  userKeyPair.publicKey,
  new YjsProvider(),
  new YjsJSONSerializer(),
  new YjsJSONSerializer(),
  new YjsJSONSerializer(),
  new SubtleCrypto(),
  new YjsACLProvider(),
  new YjsKeychainProvider(),
);
await swarm.initialize(defaultConfig(defaultBootstrapConfig([])));

// Optionally connect to bootstrap peers:
// await swarm.connect(['/dns4/relay.example.com/tcp/443/wss/p2p/12D3...']);

const todos = swarm.doc('/todo-list');
await todos.open();

todos.subscribe('ui', (state) => {
  render(state.getArray<string>('items').toArray());
});

await todos.change((state) => {
  state.getArray<string>('items').push(['Ship it']);
});
```

The repository contains runnable examples that show provider setup, identity
creation, and connecting peers. See the [quick start](getting-started/quick-start/)
to run them locally.

## How it works

1. **Edit locally.** A provider applies each change to the local CRDT replica.
   The application sees changes immediately — no network round-trip.
2. **Store, sign, encrypt, publish.** Peerborne encrypts and stores the change
   payload under a CID, then signs the complete sync message when enabled,
   encrypts its serialized envelope, and publishes that full envelope through
   GossipSub.
3. **Authenticate and merge.** Recipients decrypt the envelope, verify its
   outer signature against known writers when enabled, apply inline history,
   and fetch only missing or deferred CID payloads. The Yjs or Automerge layer
   reconciles delivered concurrent edits.

Peerborne currently verifies a signed, distinct-identity invitation and fresh
Automerge edits in both directions across a Circuit Relay boundary in CI.
Broader partition/rejoin, persistence, public WSS deployment, and relay-failover
coverage remains active work.

## Key design choices

| Choice | Rationale |
|---|---|
| **End-to-end encryption** | Infrastructure that lacks the document key carries document-key ciphertext (AES-GCM by default); ECDSA P-384 authenticates sync-envelope signers when enabled. |
| **Content-addressed storage** | Encrypted serialized change payloads are immutable under their CIDs. |
| **Shadow sync graph** | Encrypted sync messages carry CID-keyed change trees rather than embedding graph links in stored payloads. Concurrent edits coexist; the CRDT layer resolves delivered changes. |
| **CRDT-agnostic core** | Peerborne wraps Yjs and Automerge without coupling to either. Swap CRDT implementations without changing your application. |
| **libp2p networking** | Battle-tested peer-to-peer stack: WebSockets, WebRTC, WebTransport, Circuit Relay v2, GossipSub. |
| **Q-of-K quorum loading** | Require matching served-frontier hashes from distinct connected peers before binding a selected response. This reduces single-peer risk but does not prove complete interior history. |
| **BeeKEM key sharing** | Dynamic group key encapsulation. Add and remove readers without re-encrypting the document. |

See the [architecture page](concepts/architecture/) for detailed diagrams of the
data flow, networking stack, and encryption model.

## How Peerborne compares

| Tool | Use case | Server role |
|---|---|---|
| **Peerborne** | Encrypted peer-to-peer CRDT documents | Self-hosted relay/bootstrap; document payloads end-to-end encrypted |
| **Yjs** | High-performance CRDT runtime | Bring or configure a sync provider |
| **Automerge** | JSON-like CRDT documents | Configure Repo storage/network adapters |
| **Liveblocks** | Real-time presence + collaboration | Managed backend service |
| **RxDB** | Local-first NoSQL database | Flexible replication to many backends |
| **Jazz** | Local-first relational database | Managed or self-hosted sync server |
| **Electric Sync** | Sync Postgres data to clients | Postgres read-path sync engine |

Peerborne is designed for **end-to-end encrypted documents** that sync through
**self-hosted relay infrastructure without exposing document plaintext**. Relays
can still observe connection and traffic metadata. See the
[full comparisons](reference/comparisons/) for detailed trade-offs against each
project.
